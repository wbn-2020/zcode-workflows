# zcode-workflows

面向 ZCode 的需求规划与代码实施工作流。用两个日常入口，把一句需求、一份文档或一个问题现象，推进为可审阅的实施方案和有检查记录的代码交付。

- **`task-plan`：先分析，再出方案。** 读取需求和仓库，完成必要调查、选型与任务拆解，经过独立评审后交付 `plan.md`。
- **`task-run`：按方案实现，再复核验收。** 核对方案与权限，按依赖实施任务，执行独立代码复核和获授权的检查，交付执行报告。

**日常主线：描述需求 → 分析并交付方案 → 用户审阅 → 按方案实现、复核与验收 → 用户上线测试。**

规划不会自动变成施工，执行报告也不等于真实环境已经验收。是否继续执行、如何上线，仍由用户决定。

## 适合哪些场景

| 输入 | `task-plan` 本轮完成的工作 | 交付结果 |
| --- | --- | --- |
| 产品文档、功能需求 | 理解业务规则，核对现有实现，明确兼容性、接口和验收目标 | 分阶段实施方案 |
| 登录卡顿、程序缺陷、性能或内存问题 | 静态调查调用链与风险区域，独立核对候选问题 | 有确认依据的修复方案，或无须改动的调查结论 |
| 从零开发、公开项目或产品参考 | 研究公开资料，完成技术选型、架构与最小可用版本设计 | 建项任务和阶段实施方案 |

排查会在本轮实际读取代码与证据，不默认把“以后再审查代码”当作结果。没有可靠修复依据时，不为凑任务而安排改动。静态确认不等于运行时复现或性能测量。

## 快速使用

### 1. 描述需求或问题

在需要分析的项目中调用：

```text
/task-plan 看看 docs/订单需求.md，完成分析、必要选型和实施拆解
/task-plan 用户反馈登录卡，沿登录链路排查问题，给出修复方案
/task-plan 我想从零做 API 网关，参考这些 GitHub 链接，调研并设计最小可用版本
```

默认只读源码、文档和已有证据，不运行项目构建、测试、服务或压测。

### 2. 审阅方案，用自然语言修改

```text
/task-plan 修订刚才的方案，保留现有认证接口，采纳文档中的限流建议
```

技能会根据上下文选择方案路径并填写工作流参数，不要求用户手写 JSON 或 `changes=`。影响实施的业务、兼容性或成本决定会集中列出；决定未解决前，整份方案不施工。

### 3. 明确要求执行

```text
/task-run 按刚才的方案执行
```

只有方案、评审、决定、权限和源码基线全部满足要求后才开始实施。执行完成后，阅读报告中的实际变更、检查结果和人工验证清单，再安排真实环境与上线测试。

## task-plan：从需求到实施方案

### 分析与评审流程

1. 识别需求场景，读取原始输入、相关源码和参考材料。
2. 完成业务分析、静态问题调查或技术选型；候选问题由独立核对确认。
3. 拆分阶段和任务，明确依赖、文件归属、行为验收、检查命令与风险。
4. 运行结构校验并进行独立评审，回到原始需求核对遗漏，区分机器检查和人工验收。
5. 对普通方案缺陷做局部修订；自动修订全程最多三轮，交付稿另做独立复核，终审发现也共享该预算。
6. 交付方案、证据与评审材料，并说明当前是否可以交接执行。

新增问题、问题实质内容变化或引用证据变化后，需要重新独立确认。未确认的问题不能直接获得可执行修复任务。调查因上下文超限而拆分时，子任务必须覆盖原范围；遗漏会记录为缺口并停止交接。

### 方案里有什么

`plan.md` 是面向用户的阅读入口，包含：

- 分析结论、方案设计与技术选择；
- 阶段任务、依赖关系、文件范围和验收要求；
- **需求 → 实施任务 → 任务检查**覆盖表；
- 风险、假设、不做范围和待确认决定；
- 上线、迁移、回退和观察安排；
- 修订时的实际差异摘要。

覆盖表展示引用关系，不自动证明每条业务标准都被覆盖或满足。作者和独立评审仍需核对原始需求，不能把影响实施的关键未知条件藏在普通假设中。详细调查、任务书、证据和评审保存在支持目录。

| 方案状态 | 含义 |
| --- | --- |
| **可交接** | 校验与评审通过，影响实施的决定已确定；用户可以要求进入执行 |
| **待确认** | 方案与待决定事项已列出，整份暂不施工 |
| **未完成** | 证据不足或修订未通过，保留已有材料和旧方案，说明缺口 |

### 修改方案时如何处理

未受影响的任务、检查和旧决议由代码保留；新增文件、模块或依赖会补充相关调查。用户决议必须有明确原话依据。

修订摘要直接比较**旧方案与最终方案**，列出任务增改删，以及需求、检查、决定、文件范围等变化。仅修改检查定义时，也会标明受影响的任务；摘要随支持材料一起绑定，不依赖方案作者自报。

尚未通过校验的初稿检查可以纠正确实非法的字段，但不能借此弱化已有合法命令，或扩大权限与写入范围。

## task-run：按方案实施并交付

### 执行流程

1. **整份预检**：核对方案与评审、未决决定、批准与检查授权、支持材料摘要及相关源码基线。
2. **安排依赖顺序**：根据任务和祖先阶段依赖、文件冲突安排执行批次。
3. **实现与独立复核**：独立任务并行准备暂存变更；共享文件、父目录冲突、存在依赖或不适合暂存的任务串行处理。
4. **核对并应用变更**：控制器验证目标归属和原始文件摘要，再串行应用暂存内容。事务临时文件与回滚备份在独占目录中提前准备并核验，不删除实施员目录中的未知文件。
5. **运行获授权的检查**：按进度执行任务检查、已配置的阶段集成检查和最终整体检查，失败按模式与修复预算处理。
6. **核对最终现场并交付**：取得有效最终快照，比较实际文件变更，保存复核、检查与交付记录。

快照不可读、方案或源码漂移、缺权限、新业务决定不属于普通验收失败，不能调用修复任务绕过。

### 两种执行模式

模式在规划时确定，执行时从方案合同继承。

| 项目 | 标准模式 `standard`（默认） | 严格模式 `strict` |
| --- | --- | --- |
| 选择方式 | 默认使用 | 用户明确指定 |
| 执行批准 | 通过工作流运行确认授权施工 | 还需明确批准当前方案版本 |
| 检查命令 | 默认直接传程序与参数，采用危险命令黑名单 | 使用受控的测试、构建参数 |
| Shell 检查 | 必须在方案和执行两端明确同意 | 禁止 |
| 普通缺陷修复 | 原范围内最多修复一次 | 不自动修复重试 |
| 失败处理 | 默认停止；明确设置 `stopOnFailure=false` 时，可继续无依赖关系的任务 | 首个失败即停 |
| 既有未提交改动 | 只允许任务范围外的既有改动 | 除方案材料和入口外，要求工作区干净 |

明确批准当前严格模式方案可以直接作为执行授权，不需要手动修改合同。服务、远端操作和部署检查，无论哪种模式都需要额外明确授权。

### 执行报告里有什么

- 各任务的状态、每次实现尝试和独立复核结果；
- 基线与有效最终快照核对得到的实际变更文件；
- 实际运行的检查命令、退出码和输出；
- 失败原因、检查点和可行的下一步；
- 尚需人工或真实环境验证的行为，以及上线、迁移、回退和观察清单。

**报告只描述已有证据支持的结果：**

- 零任务诊断明确说明“无需施工，未运行项目验收”。
- 未配置或未运行的检查，不宣称通过。
- 未取得有效最终快照时，空变更清单不等于零改动。
- 退出码为 0 不等于所有业务行为已经通过。
- 上线清单是待人工执行的计划，不是已经完成的操作，也不构成新增授权。

工作流不会自动提交、推送或部署。

## 安全边界与版本兼容

- **不可变方案包**：v3 的 `plan.md` 使用短合同指针引用完整方案，数据保存在 `.zcode/task-plans/<输入摘要>/v-<内容摘要>/`；执行记录位于 `.zcode/task-runs/`。
- **内容绑定**：`reviewedPlanSnapshot` 使用排序 JSON，`reviewedReviewHash` 校验评审；合同指针与支持文件使用原始 UTF-8 文件内容的 SHA-256。摘要与确认令牌不是身份签名。
- **授权不能推断**：`check.permission` 只是声明。服务、远端或部署检查必须明确授权当前包的具体 `check:<id>`，缺授权时不能先执行部分任务。
- **硬性阻塞不能绕过**：确认令牌只绑定当前方案与确认原因，不能覆盖拒审、篡改、缺证据、未决实施决定或源码基线冲突。
- **保留现场**：Git 项目核对提交、分支、储藏记录（Git stash）、索引、文件内容与模式。没有 Git 的空目录使用文件系统快照；已有 Git 但尚无首个提交时仍核对分支、索引和状态，不自动初始化或提交。
- **版本兼容**：支持合法 v2 合同的串行执行；v3 提供不可变方案包、安全执行批次、分层验收和恢复检查点。v1 及没有合同的手写 Markdown 不执行。
- **不是系统沙箱**：路径、摘要和文件归属校验不能替代操作系统隔离。项目检查与获准使用的解释器仍以当前用户权限执行。

## 中断后如何继续

分析材料与执行证据会随进度持久化保存。文件写入与界面发布分别记录，界面发布失败不会要求重做已经应用的代码。

| 停止原因 | 下一步 |
| --- | --- |
| 缺批准、检查权限或业务决定 | 用户补充明确授权；业务决定交回 `task-plan` 更新并复核 |
| 可恢复的技术中断 | 先重新核对检查点、方案包和当前源码，预检通过后才恢复 |
| 范围、接口、行为或验收需要变化 | 结合当前方案、执行报告和检查点，返回 `task-plan` 重新规划 |

v3 恢复前，技能会在项目根目录调用随附的 `scripts/preflight.cjs`。已停止的运行可用 `ResumeWorkflowRun` 原样继续；脚本错误或需要修订脚本时用 `AmendWorkflow`。用户主动停止的运行，只按用户要求恢复。修订运行缺少参数时，从检查点恢复原输入、授权、停止策略、语言、预算和已应用归属，不扩大权限。

恢复必须核对成功实施、独立复核、前后快照及摘要绑定。`appliedTaskIds` 或空结果数组不能替代成功证据；阻塞、拒审和证据缺失不会经恢复变成成功。无法证明中断状态、源码被另行修改、最近检查仍失败或预算耗尽时，安全停止并保留现场。

宿主恢复可能重放已有检查记录，**不代表本次重新运行了检查**。已经完成的方案包只有当前现场与最终快照一致，才返回既有结果，不重复施工。

v2 没有这套恢复检查点。实施中断后先只读核对旧记录和当前源码，不自动恢复或重跑整包。用户仍可用自然语言表达下一步意图；返回规划也不会豁免源码基线与未提交改动保护，不自动启动下一轮规划或执行。

## 安装与目录

使用时需要同时安装工作流定义和配套技能。技能负责自然语言入口与参数整理，工作流负责实际编排。

| 内容 | 仓库位置 | 全局安装位置 |
| --- | --- | --- |
| 两个工作流定义 | `.zcode/workflows/task-plan.dwf.ts`、`task-run.dwf.ts` | `~/.zcode/workflows/` |
| 两个配套技能及辅助文件 | `.agents/skills/task-plan/`、`.agents/skills/task-run/` | `~/.agents/skills/` 下的同名目录 |
| 共享核心与开发辅助程序 | `.zcode/workflows/_task-core.ts`、`scripts/` | 开发时使用，由同步程序嵌入工作流与技能 |
| 隔离测试 | `tests/` | 开发时使用 |

配套技能目录需要包含 `SKILL.md` 和 `scripts/`，不能只复制说明文件。项目内的同名定义可能优先于全局版本，更新时应核对实际使用的副本。

两个已保存工作流都是自包含脚本，运行时不依赖本仓库的源码导入。

## 开发与验证

需要 Node.js 24.18 或更新版本。修改共享核心或辅助程序后，先同步生成副本，再进行验证：

```sh
npm run sync
npm test
npm run check
npm run check:host
```

| 命令 | 检查内容 |
| --- | --- |
| `npm run sync` | 将共享核心和辅助程序同步到两个工作流及技能目录 |
| `npm test` | 使用当前源码、模拟调用和隔离临时目录运行回归测试 |
| `npm run check` | 检查语法与官方工作流接口的严格 TypeScript 类型 |
| `npm run check:host` | 在受限环境中检查实际宿主的分析、结果结构与编译转换过程；生成代码只解析，不执行 |

测试不启动真实 `task-run`，不运行用户业务项目的测试或服务。类型检查需要可用的 TypeScript 与官方工作流技能文件，可分别通过 `ZCODE_TYPESCRIPT`、`ZCODE_WORKFLOW_SKILL` 指定位置；宿主文件可通过 `ZCODE_HOST_BUNDLE` 指定。

宿主检查依赖非公开接口并绑定已复核版本的文件摘要，默认路径与本机环境有关。宿主升级后会拒绝继续，需要重新复核。检查通过不代表模型可用性、实际模型输出或运行期权限已经验证。

模型、网络和宿主仍可能中断；本项目提供的是证据保存、明确交付和受控恢复，不保证永不中断或上线零缺陷。
